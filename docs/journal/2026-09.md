## 2026-09-22 08:55 — `.IC V(node)=` is honoured, not accepted-and-dropped

[#12](https://github.com/GLODI-Engineering/general-mna/issues/12), the second leftover from
the 2026-09-21 20:52 entry. `V1 a 0 10 / R1 a b 1000 / C1 b 0 1e-6 / .IC V(b)=5` started at

  its `ConflictingConditions` / `InconsistentWithCircuit` checks then apply unchanged, so a

- `hierarchy.rs` forwards non-element statements untouched, so a top-level `.IC` reaches the
  builder through `build_system` too (tested). A `.IC` *inside* a `.subckt` body is not
  node-mangled; its inner node name then fails the "no element connects to" check rather than
  silently binding to the wrong node — acceptable for now, noted here.

## 2026-09-21 20:37 — an `ic`-free inductor current is determined, not free

[#6](https://github.com/GLODI-Engineering/general-mna/issues/6), fixed by
[#7](https://github.com/GLODI-Engineering/general-mna/pull/7).
`check_assignment_against_circuit` (`src/numeric.rs`) skipped every row holding an unknown
without an `ic`, reasoning that the first solved step re-imposes it. True for node voltages and
source branch currents; false for an inductor branch current, which `initial_state` pins at
zero and the integrator then takes as the real initial current. On an inductor cut-set with an
`ic` on some branches only, the contradiction was accepted silently (declared inductors started
at the average of the requested currents, a node rang to about a megavolt). Inductor branch
currents — `I(...)` unknowns with a nonzero `K` row — now count as assigned whether or not they
carry an `ic`, so the existing `InconsistentWithCircuit` error fires.

Deliberately *not* widened to `ic`-free capacitor node voltages: those are shared with the
resistive network and genuinely re-imposed, and the wider rule rejects an ideal source beside an
`ic`-free capacitor, which is correct, documented behaviour.

## 2026-09-11 06:18 — check positional device-card parameters too; `ic=` becomes an assignment

Follow-ups to the entry below, filed as
[#4](https://github.com/Elvis-codeur/general-mna/issues/4) and
[#5](https://github.com/Elvis-codeur/general-mna/issues/5) (cross-referenced from
`general-simulator`'s #1/#2/#4).

**#4 — the other half of the silent-drop hole.** The previous pass checked `key=value` tokens on
every stamped letter but positional tokens only on `R`/`C`/`L`, on the grounds that the other
grammars were "open". They are open, not unbounded. `src/builder.rs` now carries a
`PositionalGrammar` per letter and a `positional_grammar(element)` that picks it:

- `OneValue` — `R`/`C`/`L` (the element value), `K` (the coupling coefficient;
  `general-spice-core` puts every earlier token in `nodes` as an inductor name), and `E`/`G` in
  the classic four-node form (the gain).
- `ControlAndGain` — `F`/`H`: a controlling source's name, then a gain. The name itself is still
  checked later and separately, by `UnknownControllingBranch`.
- `SourceClauses` — `V`/`I`: a bare leading DC value and/or `DC <value>`, an
  `AC <magnitude> [<phase>]` specification, and at most one `SIN`/`PULSE`/`EXP`/`PWL`/`SFFM`
  call whose arguments are re-parsed through `TransientFunction::parse` so a wrong argument
  count fails here rather than silently defaulting.
- `DiodeModel` — `D`: a model name, an optional area factor, an optional `OFF`.
- `None` (skip the card entirely) for the two-node behavioral `E`/`G` form
  (`E1 out 0 VALUE={...}`), which this crate does not stamp at all: field-checking it first
  would replace `four_nodes`' accurate "requires the classic four-node linear form" with a
  misleading `unknown field 'value'`.

`M`/`Q`/`J` are deliberately left exactly as they were, and the reasoning is worth recording
because it is the question #4 actually asked. Those letters are governed by
`UnsupportedElementPolicy`: under `Error` the card is already rejected outright, and under
`IgnoreWithWarning` the caller has *explicitly asked* for an unmodeled device to be tolerated
with a warning. Rejecting its parameters would override that instruction with a hard error over
a token this crate was never going to read — a strictly worse outcome than the warning the
caller asked for, and a different decision from the one this validation makes (which is about
cards we do stamp and parameters we do read). The README now lists this, a diode's model name,
a symbol in an `AC` magnitude, and a switch-assigned element's positional value as the four
things a typo can still hide in.

**Two silent drops found while writing the validator**, both fixed because a validator that
blesses a token the builder then ignores is worse than no validator. `TransientFunction::parse`
only ever looked at `tokens[0]`, so `V1 1 0 DC 0 SIN(0 10 1000)` — ordinary SPICE — parsed the
DC clause and dropped the whole waveform, simulating a flat 0 V source. New
`TransientFunction::find_call`/`parse_params` locate the call anywhere in the parameter list;
`parse` is unchanged and stays the primitive that assumes the slice starts at the call. And
`source_value` read `params.first()` when there was no `DC` token, which turned `V1 1 0 AC 1`
into a source whose value was a *symbol named `AC`*; it now reads only the DC clause and falls
back to zero, SPICE's own default, for a card that declares none.

`TransientFunction::FUNCTION_NAMES` is now the single list of accepted function names, with a
unit test asserting `parse` accepts exactly those, so the validator and the parser cannot drift.

**#5 — `ic=` is an assignment now, not a solve.** The previous entry implemented `ic=` as a
constrained operating point: each `ic`-bearing capacitor held as an ideal voltage source, each
`ic`-bearing inductor as a current source, `ic`-free storage opened or shorted, and the whole
modified system solved. That is a consistent operating point, but it is not what a netlist's
`ic=` means. "Use initial conditions" means the operating point is *skipped*.

`MnaSystem::initial_state` now assigns and does not solve. `A`/`K`/`B`/`u` are untouched, no
element is swapped for a source, and no auxiliary unknown is introduced — so the `unknowns`
ordering contract cannot move, which it previously only survived because the auxiliaries were
appended and dropped. An `ic`-bearing inductor's own `I(<name>)` is set to its declared current;
everything else stays at rest.

A capacitor's condition is about *two* unknowns, not one, which is the only genuinely awkward
part. The `ic`-bearing capacitors are treated as a graph over nodes (one edge per condition,
ground as an extra vertex pinned at zero) and each connected component's potentials are
propagated breadth-first from a root at zero — ground when the component touches it, otherwise
the component's lowest-indexed node, since a floating island's absolute potential is not
something the netlist declared. This is what makes a series chain come out right
(`C1 a b ic=3` + `C2 b 0 ic=2` gives `V(b) = 2`, `V(a) = 5`) in either card order; a naive
per-card assignment in netlist order leaves `V(a)` stale at 3.

**Reporting, not overriding.** Two distinct failures, deliberately separate:
`ConflictingConditions` for `ic` values that contradict *each other* (a capacitor loop whose
declared voltages do not sum to zero — no circuit equation involved), and
`InconsistentWithCircuit` for an assignment that violates one of the circuit's own algebraic
equations. The second check is narrow on purpose: only rows whose `K` row is entirely zero (a
row with storage in it describes a derivative, and its residual at `t = 0` is the current that
starts flowing, not a contradiction), and among those only rows *every* one of whose unknowns is
assigned (a row with a free unknown is one the circuit can still satisfy, and the first solved
step is where that happens). That narrowness is what makes it fire exactly on the two textbook
cases — an `ic` across an ideal voltage source (`I(V1)`'s branch row, residual −5 for
`V1 a 0 10` + `C1 a 0 ic=5`) and series inductors declaring different currents (`V(b)`'s KCL
row) — without false positives on every ordinary deck.

**The observable difference, in numbers.** `V1 a 0 10` / `R1 a b 1000` / `C1 b 0 1e-6 ic=5`:
the solve answered `V(b) = 5`, `V(a) = 10`, `I(V1) = -5 mA`; the assignment answers `V(b) = 5`
and zero for both of the others. And for a deck whose capacitor declares *no* `ic`
(`R1 a b 1k` / `R2 b 0 1k` / `C1 b 0 1u`, alongside an `ic`-bearing inductor elsewhere), the
solve opened `C1` and handed back `V(b) = 5` — a capacitor pre-charged by a circuit that had not
run yet — where the assignment answers 0.

**Not added, deliberately.** The old solve is a genuinely useful thing to want (a "start in
steady state with these states held" run), but nobody asked for it and guessing at the interface
is how a public API accumulates two half-specified ways to do one thing. If it comes back it
should come back as a named second entry point (`initial_state_consistent`, say) with its own
issue, not as a boolean on this one.

**Gate.** `make test` green: `cargo fmt --all -- --check`, `cargo clippy --all-targets
--features python -- -D warnings`, `cargo test --all-targets` (32 + 47 + 5 + 23 tests), the
Python binding unit tests, and `scripts/validate_notebooks.py`.

## 2026-09-11 05:49 — reject unknown device-card fields; support `ic=` on `C`/`L`

Two related requests, filed as [#2](https://github.com/Elvis-codeur/general-mna/issues/2) and
[#3](https://github.com/Elvis-codeur/general-mna/issues/3) here (cross-referenced from
`general-simulator`'s own #1/#2, where the symptom was first noticed).

**What was found.** `general-spice-core` captures every trailing token of a device card
faithfully in `ElementInstance::raw_params`; this crate then read only `raw_params.first()` in
`scalar_value`/`source_value` and dropped the rest without a word. Reproduced independently
against the release CLI at `general-simulator` 7067c20: `C1 b 0 1e-6 ic=5` and the same deck
with `wibble=5` produced byte-identical CSV. Meanwhile the block (`kind=...`) path in
`system_builder.rs` *is* strict and emits good `line N: device '<name>' ...` diagnostics — the
device-card path simply never caught up.

**What changed (`src/builder.rs`).** A `validate_trailing_fields` pass runs over every element
this crate has a stamp for, before any indexing or stamping, so a bad field is the first thing
reported. It rejects (a) any `key=value` token whose key is not accepted for that device letter
and (b) an extra positional token on `R`/`C`/`L`, whose value list is closed at exactly one
entry. Deliberately *not* checked: unstamped letters (an `M` card's `L=1u W=10u` is valid
netlist text this crate has no model for, and checking it would turn `IgnoreWithWarning` into a
hard error), and the open positional grammars on `V`/`I`/`D`/`E`/`F`/`G`/`H`/`K` (`DC`/`AC`
specifiers, transient-function tokens, model names, controlling-source names, a variable-length
inductor list) — only their `key=value` tokens are checked, which is where the silent drop
actually bites. New `BuildError::InvalidElementField { line, name, message }` carries the
element's own `span.start`, and formats as `line N: device '<name>' ...` to match
`system_builder.rs` exactly.

`system_builder::build_system` now renders a `BuildError` with `Display` instead of `Debug`; the
new variant's whole point is a readable sentence, and a struct dump buried it.

**What changed (`ic=`).** `MnaSystem` gained `initial_conditions: Vec<InitialCondition>`
(`src/system.rs`), resolved against the unknown ordering at build time and deliberately kept out
of `A`/`K`/`B`/`u` — an initial condition constrains `x` at one instant, it does not change the
circuit's equations. `MnaSystem::initial_state(values, tolerance)` (`src/numeric.rs`) turns them
into a starting vector, returning `Ok(None)` for a netlist declaring none so a caller keeps its
own "start from rest" default.

It is a solve, not an assignment: the other unknowns are not free. At `t = 0` each `ic`-bearing
capacitor becomes an ideal voltage source and each `ic`-bearing inductor an ideal current
source (its branch equation `v = L*dot(i)` replaced in place by `I(<name>) = ic`, keeping its
node incidence so its current still flows), while `ic`-free capacitors open and `ic`-free
inductors short. The auxiliary branch-current unknown each `ic`-bearing capacitor needs is
appended *after* every existing unknown and dropped from the result, so the `unknowns` ordering
contract does not move and a capacitor floating between two non-ground nodes works like any
other. A contradictory `ic` or a node left without a DC path is `InitialStateError::Singular`,
not a silently meaningless vector.

**Sign conventions**, spelled out on `InitialCondition`, on `initial_state`, and in the README:
a capacitor's `ic` is first node minus second; an inductor's `ic` is the current from the first
node to the second *through the inductor*, which is exactly the sign of the system's own
`I(<name>)` unknown because `stamp_branch_incidence` puts `+1` in the first node's KCL row.
Tests pin both, including the reversed-terminal case, because this is the half that gets
misremembered.
