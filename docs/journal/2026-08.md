## 2026-08-24 14:39 — External signal binding into a subckt's block graph (Phase 3 follow-up)

The previous Phase 3 entry deferred binding a signal from *outside* a `.subckt` instance into
its own internal block graph, on the assumption it would need new port-domain-inference logic
and an extended `X`-line syntax. Turned out unnecessary: `hierarchy::flatten`'s `port_map`
substitution is already domain-agnostic — it resolves a name via the caller's binding or falls
back to dotted-path prefixing, with no idea whether that name is an electrical node or a signal.
Since `mangle_block` already runs the *same* `resolve` closure `expand_body` uses for electrical
element nodes, declaring an extra "port" purely to carry a signal binding — no electrical meaning
at all — already worked, with zero code changes needed.

Two directions, both confirmed by test and by an end-to-end CLI smoke run:

- **Signal in**: `.subckt reg vin vout ctrl` with an internal block field `in=ctrl`; calling
  `X1 vsrc vload EXT_DUTY reg` binds `ctrl` to `EXT_DUTY`.
- **Signal out**: an internal block whose own `.name` *is* the declared port name becomes
  addressable from outside under whatever the caller bound that port to — symmetric with how an
  internal node named the same as an electrical port already works.

Rewrote `hierarchy.rs`'s module doc comment (previously claimed this was unsupported) to document
both directions with worked examples. Added two new unit tests
(`a_signal_can_be_bound_into_a_subckt_instance_from_outside_via_a_declared_port`,
`a_subckt_instance_can_expose_an_internal_block_as_a_signal_output_port`) — 27 tests total now,
all passing. Verified end-to-end through `general-simulator`'s real CLI binary: a MOSFET declared
inside a `.subckt` body, gated via a declared `ctrl` port bound to an externally-declared
`kind=const` → `kind=sig2gate` chain, correctly switches on (`vout ≈ 5·1000/1000.1V` for a
0.1Ω on-resistance switch, matching hand calculation).

`cargo fmt`/`clippy -D warnings`/`test --workspace` all clean.

## 2026-08-24 14:32 — Phase 3: `.subckt`/`X`-instance hierarchical flattening

Added `hierarchy::flatten` (new module `src/hierarchy.rs`): expands every `.subckt`/`X`-instance
pair in a parsed `Statement` list into one flat list, dotted-path-prefixing every internal
device/block name by its instantiation chain (`X1.R1`, `X1.X2.C3`, ...) so repeated instances of
the same subcircuit never collide. Handles nested subckt instantiation (dotted paths compose),
positional port binding (a `.subckt`'s declared node list ↔ the `X`-call's own node list),
recursive-instantiation detection (a cycle errors instead of infinite-looping), and node-count
mismatches — all with clear `Result<_, String>` errors. Block/signal-domain statements
(`Statement::BlockInstance`) declared inside a `.subckt` body are flattened the same way: the
block's own name and every signal-reference field (`in`/`inputs`/`ctrl`/`clamp_lo_in`/
`clamp_hi_in`, `prev:`-prefixed values handled) get the same dotted-path resolution; `outputs=`
entries are always instance-prefixed (new names, never references).

**Scope explicitly deferred, not an oversight**: binding a signal from *outside* a subckt
instance into its internal block graph (a genuine signal-domain port) isn't implemented this
pass — every block reference inside a body must resolve within that body or through an
electrical port. This was surfaced to and confirmed acceptable by the user before implementation;
a real narrowing relative to the original Phase 3 plan text, which mentioned this as in-scope.

**Real bug caught by end-to-end smoke-testing, not by the unit tests**: ground (`"0"`/`"gnd"`,
case-insensitive) was initially being dotted-path-mangled like any other node inside a subckt
body, turning a capacitor's ground terminal into a private, per-instance node instead of the one
true globally-shared reference — silently open-circuiting it (a capacitor whose only other
terminal is an untouched private node carries zero current by KCL). Caught by building a
two-stage RC-lowpass-via-subckt netlist and running it through the real CLI: the output showed no
actual RC time-constant behavior at all (just the source's own built-in ramp shape passing
through what was effectively a bare resistor divider) even though every unit test passed. Fixed
by special-casing ground in `hierarchy::flatten`'s node-resolution closure to never be mangled or
port-substituted; added a dedicated regression test
(`ground_inside_a_subckt_body_stays_the_global_reference_not_a_private_node`) exercising exactly
this two-instance-RC-leg shape. Re-verified end-to-end afterward: the same netlist now shows a
correct ~1ms (`R*C = 1k*1uF`) charge/discharge curve per stage.

New public API: `general_mna::parse_and_flatten(source, dialect) -> Result<Vec<Statement>,
String>` (parse + flatten, the shared first step `build_system` itself now uses) — exposed
specifically so `general-simulator`'s `dae-runtime` crate can flatten once and reuse the same
statement list for its own from-scratch `MnaSystem` rebuilds (per-timestep switch-state
rebuilding needs fresh `MnaBuilder::build_statements` calls, not a single cached `MnaSystem`) —
see `general-simulator`'s own journal entry for that side of the integration, which was the
larger part of this work (`dae-runtime` previously re-parsed raw netlist text independently at
~10 call sites, completely bypassing hierarchy).

8 new tests in `hierarchy.rs` (7 `flatten` behavior tests + the ground regression), 1
`system_builder.rs` test updated to instantiate its subckt explicitly (uninstantiated subckt
bodies correctly contribute nothing now, a real, intended behavior change from Phase 2's
"leaks to top level unconditionally" — Phase 2's own test asserted the pre-hierarchy behavior).
`cargo fmt`/`clippy -D warnings`/`test --workspace` all clean.

## 2026-08-20 11:20 — Fix: `TransientFunction::parse` rejected SPICE-suffixed arguments

Follow-up to the entry directly below. While smoke-testing the new time-varying sources
end-to-end through `elspice-pwl`'s real CLI (not just this crate's own unit tests, which only
ever used plain numeric literals), `PULSE(0 5 1m 100n 100n 2m 4m)` — an entirely ordinary
netlist line — failed to build at all: `unsupported scalar expression 'PULSE(0'; use a number
or symbol`. Root cause: `TransientFunction::parse`'s numeric-argument parsing used raw
`str::parse::<f64>()`, which doesn't understand SPICE suffixes (`1m`, `100n`, ...); it failed
silently via `?`, so `parse()` returned `None` and the whole source fell through to the old,
now-inapplicable scalar-only path, which then correctly rejected the leftover `PULSE(0` token
as garbage. Confirmed via a scratch probe that `spice-core`'s own tokenization was not at
fault. Fixed by making `expression::parse_spice_number` `pub(crate)` and calling it directly
from `transient_source.rs`, instead of `f64::parse`. Added two new unit tests exercising
suffixed arguments (`PULSE(0 5 1m 100n 100n 2m 4m)`, `SIN(0 10 50k 0 0 0)`) — the exact gap
that let this through the first time. `cargo fmt`/`clippy -D warnings`/`test`/`build
--all-features` all clean. Re-verified end-to-end through `elspice-pwl-cli` for all five
source kinds afterward (tracked in `elspice-pwl`'s own journal).

## 2026-08-20 07:49 — Time-varying `V`/`I` sources: `SIN`/`PULSE`/`EXP`/`PWL`/`SFFM`

Requested directly by the user for `elspice-pwl` (the TIDA-010954 cycloconverter experiment
needed a genuinely time-varying `Vac(t)`), pointing at `spice-core`'s own grammar reference
(`spice-lsp/docs/GRAMMAR.md`) for the exact forms: the same five transient-function names
common to both ngspice and Xyce.

Confirmed directly (not assumed) before writing anything: `spice-core` already tokenizes a
`SIN(0 10 1000)`-style source losslessly — `["SIN(0", "10", "1000)"]`, parens stuck to
whichever token they landed on, but every number recoverable — so no `spice-core` change was
needed at all, only interpretation on this crate's side. Also confirmed `elspice-mna` already
has exactly the mechanism needed: a `V`/`I` source's `B` column is stamped once, generically,
by `stamp_voltage_source`/`stamp_current_source` regardless of what the source's own literal
value is — the *value* only enters via `input_values[column]`, a symbolic `Expression`
evaluated fresh on every `MnaSystem::evaluate` call. A PWL diode's own Norton current
(`{name}_Ioff`) already uses this as a per-step-overridable *symbol* rather than a baked
literal; a `V`/`I` source with a transient function just needed the same treatment, which no
prior netlist ever needed since every source so far was a plain constant.

New `transient_source` module: `TransientFunction` (`Sin`/`Pulse`/`Exp`/`Pwl`/`Sffm`, pure data
plus a pure `value_at(t) -> f64`, hand-verified against textbook values for each form — a
`PWL`'s own breakpoint list is heap-allocated, not a fixed-size inline array, after `clippy`
flagged the enum ballooning to 528 bytes for a sized-for-worst-case `PWL` even on a plain
`SIN`) and `TransientFunction::parse` (detects and reassembles a call from `spice-core`'s own
mangled tokenization). `builder.rs`'s per-source loop now tries `TransientFunction::parse`
first; if it matches, the source becomes `Expression::symbol(name)` (the diode pattern) and its
parsed function is recorded in a new `MnaSystem::transient_sources: BTreeMap<String,
TransientFunction>` field for the caller to read; if it doesn't match, exact existing behavior
(a baked literal from `source_value`) is unchanged — confirmed via a new test
(`plain_dc_source_is_unaffected_by_transient_source_support`) and the full existing suite
passing unmodified.

**This crate has no notion of "now"** — it hands the caller a `TransientFunction` and the
caller is responsible for calling `value_at(t)` and passing the result into `evaluate`'s
`values` map at every step, exactly the same delegation already used for diode Norton currents.
Wiring that into `elspice-pwl`'s own transient loop (`dae-runtime`, which currently has no
notion of "the current absolute simulated time" threaded into its `fold_and_solve` calls at
all) is a separate, not-yet-done change — tracked in `elspice-pwl`'s own journal.

`cargo fmt`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and
`cargo build --all-features` (the optional `python` binding) all clean.


## 2026-08-17 10:01 — Add 'D' (diode) stamp + numeric RHS evaluation, for `elspice-pwl`

A new sibling repo, `elspice-pwl`, is building a Newton-free piecewise-linear circuit
simulator (LCP-based mode selection instead of Newton-Raphson + voltage limiting) and needs
this crate's linear-device stamping for the non-PWL parts of a circuit. Its own diode/MOSFET
companion models are resistor-plus-current-source (`I = G*V + I_off`) between two *existing*
nodes — no new MNA unknowns needed — so the minimal, additive extension was: recognize `'D'`
as a stampable device (`src/builder.rs`), reusing the existing `stamp_admittance` +
`stamp_current_source` functions verbatim with two new per-instance symbolic parameters
(`{name}_G`, `{name}_Ioff`) instead of parsed netlist values, mirroring the `Ron`/`Roff`
pattern switches already use.

This exposed a real gap: `NumericMnaSystem::evaluate()` only evaluated `a`/`k`/`b`, never the
RHS (`u`/`input_values`) — fine while every source's value was fixed at parse time, but a
diode's `Ioff` genuinely changes every timestep. Added `input_values: Vec<f64>` and
`u: Vec<f64>` to `NumericMnaSystem`, computed the same way the symbolic `u` already is.

First attempt made input-value evaluation mandatory (error on a missing symbol), which broke
`converter_switch_phases_average_with_duty_ratio` — that test deliberately leaves `Vin`
unresolved while only checking the averaged `a`/`k` matrices, a legitimate pre-existing
pattern. Fixed by making it best-effort (`f64::NAN` for an unresolved input, contributing
`0.0` to `u`) rather than failing the whole evaluation — matches how `a`/`k`/`b` evaluation
already only requires the symbols actually needed for what's being computed.

Also updated `nonlinear_devices_are_not_silently_discarded` (its 'D' fixture is now
intentionally supported; retargeted at 'Q', which still correctly errors) and added
`diode_is_stamped_as_symbolic_conductance_plus_norton_current_source`, hand-tracing the
expected `a`/`b`/`u` expressions from the stamping functions' own source before writing the
assertions, not just checking the code runs.

Verification: `cargo fmt --all -- --check`, `cargo clippy --all-targets --features python -- -D
warnings`, `cargo test --all-targets` and `--all-targets --features python` all clean (15
tests total, all passing). Did **not** run the full `make test` gate this session — that also
builds the PyO3/maturin binding and runs the Python unit tests + notebook validation, none of
which touch the changed surface (confirmed no `NumericMnaSystem` usage in `src/python.rs`;
only the unrelated symbolic `StringMnaSystem.u`/`.input_values` fields are exposed there) —
flagging this explicitly rather than silently skipping it, per this repo's own verification
discipline. Worth running before the next Python-facing change lands.
