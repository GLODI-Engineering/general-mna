## 2026-11-28 20:07 — a .model inside a parameterised body is refused rather than dropped

[#67](https://github.com/GLODI-Engineering/general-mna/issues/67). Filed while closing
[#63](https://github.com/GLODI-Engineering/general-mna/issues/63) and deliberately left out of
it: a `.model` has exactly the property that made a body-level `.param` refusable, and had none
of the handling.

`.model DX D(IS={Isat})` inside a parameterised body was passed through untouched, so `{Isat}`
reached the solver as a symbol nothing declared — the error named the *parameter* rather than
the instance that was supposed to supply it, which is the wrong complaint in the wrong place.
Substituting it instead would have been worse than the bug: two instances would emit two
`.model DX` cards with different values and, the name being global once the hierarchy is flat,
whichever expanded last would win. That is the silent wrong answer the `.param` rule exists to
refuse, so the `.model` rule is the same rule.

What the refusal names, because a reader of it has to act on it: the model, every formal it
depends on, the line, and the instantiation path it was expanding (`X1.X9`, not just "a
subcircuit").

**Both halves are asserted**, in `tests/subckt_model_parameters.rs` (11 tests). A refusal
nothing can pass is as wrong as a drop nothing refuses: a suite that only proved a
parameterised `.model` is refused would equally cover an implementation that refused *every*
`.model` in *every* body, and that is the only kind anything in this project writes today. So
four decks are asserted to still pass — an unparameterised model in a parameterised body, one
written in terms of a global `.param` (not a formal, so not this rule's business), one at the
top level, and one in a body with no formals at all.

**The detection asks by name, not by whether substituting changed the text.** The two differ in
one case: a parameter bound to its own name (`X1 a b def Rv=Rv`, the caller declaring no `Rv`
either) substitutes to byte-identical text, which a changed-or-not test would read as
instance-independent. `formals_named_in` therefore shares its two scanners — `rewrite_segments`
and `map_identifiers`, factored out of `substitute_params` in this commit — with the
substitution itself, so the two answers about one piece of text cannot drift apart as the
grammar they scan grows. The `.param` arm now asks the same way and lists the parameters it
found; its previous `substitute(raw) != *raw` had the same blind spot.

Verification: `cargo clippy --workspace --all-targets` and `cargo test --workspace` clean, then
**four mutations**, each reverted:

| mutation | caught by |
|---|---|
| the rule removed (the `.model` arm falls through) | 5 tests |
| refuses every `.model` containing a brace | 7 tests |
| formals matched as substrings, not whole identifiers | 1 test — `a_formals_name_inside_a_longer_identifier_is_not_a_reference_to_it` |
| substitutes into the `.model` instead of refusing | 5 tests |

Remaining: nothing of this issue. The `.model`-per-instance feature a refusal points away from
— a body whose model really must differ per instance — would need the model *name* to be
mangled like every element name already is, and nothing has asked for it.

## 2026-11-27 15:03 — a .subckt's formal parameters are bound where it is instantiated

[#63](https://github.com/GLODI-Engineering/general-mna/issues/63). Both halves of the grammar
parsed long before any of it worked: `.subckt rpart p n Rv=1000` landed in `Subckt::params`,
`X1 a b rpart Rv=100` landed in the call site's `raw_params`, and **nothing read either one**.
`hierarchy::expand_body` threaded a `port_map` for nodes and had no scope at all for
parameters, so the body's `{Rv}` reached the builder as the name of a parameter nothing
declared.

**Measured before changing anything**, through a `general-simulator 0.10.0` binary built
against `general-mna` at `main`:

| deck | result |
|---|---|
| `.param Rv=330` with `R1 A 0 {Rv}` | `0,5,-0.015151515151515152` — $5\,\mathrm{V}/330\,\Omega$ |
| `.subckt RPART p n Rv=1000` instantiated `Rv=100` / `Rv=220` | `error: Evaluate(MissingSymbol): evaluating an expression failed: missing value for symbol 'Rv'` |

That near miss is the whole diagnosis. A top-level `.param` has always worked, so
`Expression`, the symbol table and every field reader were never the problem — only the
**scope** was missing. Which is why the repair is a binding pass in `hierarchy.rs` and not a
line of `expression.rs`.

**What was added.** `expand_body` carries a `params` scope beside its `port_map`.
`bind_params` builds one per instance: the definition's declared defaults, overridden by the
call site's `name=value` tail, with each override resolved in the *caller's* scope first (so
`X1 p n inner Ri={Ro}` inside a definition whose own formal is `Ro` works). `substitute_params`
then rewrites the scope into every expression segment the body expands — element values, block
fields, `.IC` values.

Four decisions worth having written down:

1. **The scope shadows rather than extends.** A body sees its own formals and whatever is
   global, never its caller's. That is SPICE's own rule, and the only one under which a
   definition means the same thing wherever it is called from. `tests/subckt_parameters.rs`
   asserts it with a resistor valued `{Ro}` inside a definition that does not declare `Ro`,
   which must stay unresolved.
2. **Only `{...}` and `'...'` are rewritten.** A bare token in a value position can be a model
   name, a device keyword or a behavioural-source fragment, so substituting a bare `Rv` would
   mean guessing which of those a two-letter token is. The grammar provides braces for exactly
   this (§5), and a netlist that wants a parameter in a value says so with them.
3. **A non-atomic bound value is parenthesised.** `{Rv*2}` with `Rv=3+1` would otherwise become
   `{3+1*2}` — 5 instead of 8, silently. A number or a bare name goes in bare, so the ordinary
   `{Rv}` with `Rv=100` still reads as `{100}`.
4. **A `.param` inside a body that depends on a formal is refused.** Its name is global once the
   hierarchy is flat, so two instances would both declare it and the last would win. That is
   only wrong when its value depends on a formal — precisely when the two instances disagree —
   so that case is refused and the independent case still passes through.

Three refusals rather than three silent repairs: an override naming an undeclared parameter
(naming the instance, the parameter, the definition and what it does declare), the same
parameter set twice, and a declared formal with neither default nor value. A dropped override
is a different circuit than the deck describes, and a mistyped parameter name is exactly how
that happens.

**Verification.** 13 tests in `tests/subckt_parameters.rs` and 6 in `hierarchy.rs`, plus
`make test` green. The physics is derived rather than recorded: $100\,\Omega$ and
$220\,\Omega$ in series across $5\,\mathrm{V}$ gives node $A$ a self-conductance of
$1/100$ and node MID $1/100 + 1/220$, both asserted off the assembled $A$ matrix. Each new
rule was then watched failing under a mutation — the caller-scope resolution removed, the
scope made to extend instead of shadow, the undeclared-override refusal disabled, the
parentheses dropped — and the acceptance deck re-run through a rebuilt
`general-simulator`, which now solves it: `0,5,3.4375,-0.015625`, i.e. $5/320\,\mathrm{A}$ and
a mid-node at $5 \times 220/320$.

**What this unblocks.** `gsim-core` emits neither the formal list nor the instance tail today
(it stores both and drops them), and its decision 0010 now carries the ordering rule: the
compiler must not emit a parameter until a `general-simulator` release carries this. So the
next steps are a `general-simulator` release and then `gsim-core#111`.

## 2026-11-26 03:20 — every netlist number is finite now, not just every capture sample

[#54](https://github.com/GLODI-Engineering/general-mna/issues/54), the design question #48
deliberately did not answer. `parse_spice_number` fell back to Rust's own float parser, which
accepts `nan`, `inf` and `-inf`, and #43 had made that function the single grammar for every
number a netlist carries — so the hole was uniform and silent.

**Reproduced before changing anything**, and it is worse in more ways than the issue listed.
`tests/non_finite_numbers.rs` has the table; the builds it recorded on `main` were:

| deck | what it built |
|---|---|
| `R1 in 0 nan` | $A = \begin{bmatrix}\text{NaN} & 1\\ 1 & 0\end{bmatrix}$, and the solve returns NaN for every unknown |
| `V1 in 0 nan` | $u = [0, 0]$ — `MnaSystem::evaluate` drops a NaN input value, so the source silently became $0\text{V}$ |
| `R1 in 0 inf` | a conductance of exactly $0$: a silent open circuit, and here a singular system |
| `R1 in 0 -inf` | a conductance of $-0$ |
| `C1 in 0 inf` | an infinity in $K$ |
| `.param rl=nan` | the NaN reaches $A$ through every device that names the parameter |
| `r_on=nan` | `shared_r_on` is NaN, and it is handed to `general-simulator` outside the matrix entirely |

The source case is the one worth singling out: it does not even produce a NaN. The run
completes and reports plausible numbers for a circuit whose supply is not the one written down.

**The refusal is in `parse_spice_number`**, which is the smaller of the two options the issue
weighed and the right one. Every field reader becomes finite-only at once, and each one's own
message — which already names the line, the device and the field — does the reporting. No field
wants an infinity today: `pw`, `per` and `td2` spell "effectively unbounded" as `f64::MAX / 4.0`
rather than as an infinity, deliberately.

Three places needed more than that:

- `Expression::parse_scalar` refuses it explicitly, *before* its symbol fallback. `nan` and
  `inf` are simple symbols by spelling, so without that branch `R1 in 0 nan` would have become
  a reference to an undeclared parameter called `nan` and been reported much later, somewhere
  else, as a missing symbol.
- `builder::is_value_token` asks about *shape* only, so it still says yes to a non-finite
  literal. Otherwise `V1 in 0 nan` would have been reported as a card whose third token is in
  an unexpected position, rather than by the reader of that value, which can say what is wrong
  with it.
- A `.param` default with a non-finite value is a hard error, new `BuildError::InvalidParam`,
  rather than the existing warning for an expression this crate cannot evaluate. The warning
  drops the default, and every device written `{name}` then reads as an undeclared symbol.

`wave_file::number_at` keeps #48's own `NotFinite` refusal by asking the new
`parse_spice_number_allowing_non_finite`: its message names the file, the line and the column,
which a message about a netlist field cannot. `starts_with_a_number` asks the same, for the
same reason the decimal-comma case is admitted there — a row of `nan` must reach the refusal
that explains it, not be skipped as preamble so the file reports "no line begins with a number".

**Breaking**, in two ways worth naming: `BuildError` gains a variant, and a deck that used to
build now fails. The second is the fix.

**Verification.** `make test` (`cargo fmt --all -- --check`, `cargo clippy --all-targets
--features python -- -D warnings`, `cargo test --all-targets`, the Python binding's unittests,
`compileall`, `validate_notebooks.py`) — green, exit 0. `make artifacts` not rerun: no
equation, converter model, binding or generator changed, and `validate_notebooks.py` passed
against the committed notebooks.

## 2026-11-19 22:09 — a capture holds no NaN

[#48](https://github.com/GLODI-Engineering/general-mna/issues/48), found by the corpus in #47.
`parse_spice_number` falls back to Rust's own float parser, which accepts `nan`, `inf` and
`-inf`, and nothing in the loader asked it not to. A clipped sample therefore became a
breakpoint, and the first step that interpolated across that segment returned NaN for the rest
of the run — with nothing anywhere naming the capture as the cause.

**The time column was the worse half.** The monotonicity check is `if time < previous`, and every
comparison with NaN is false, so a NaN timestamp passed it. The breakpoint list it admitted had
no total order at all, and `segment_before`'s `partition_point` is documented as returning an
*unspecified* index on an unsorted slice — so the waveform was not wrong in some bounded way, it
was arbitrary. That is why the check could not live in the ordering test: by the time the
ordering test could see the problem it had already been defeated by it.

The refusal is a new `WaveFileError::NotFinite` in `number_at`, which is the one place every
time and every value in a capture passes through, so one check covers both columns. Its message
says why `nan` is not a number *here*, which `NotANumber` could not: a capture records a real
signal, and no sample of one is `nan` or `inf`.

Refused in the loader rather than in `parse_spice_number` deliberately, so that only the
loader's contract changed. The same hole is open one level up — `R1 in 0 nan` and `C1 in 0 inf`
both build a netlist today, and solve to NaN everywhere — and that is
[#54](https://github.com/GLODI-Engineering/general-mna/issues/54), because the answer there has a
design question in it (`parse_spice_number` itself, or each field reader?) that this fix did not
need to answer.

Two fixtures went into the corpus with the fix: `nan-timestamp.csv` for the time column and
`infinite-sample.csv` for the other spelling. The corpus test that pinned the old behaviour now
asserts the refusal, which is what a pinned defect is for.

## 2026-11-19 22:03 — nineteen shapes a capture can arrive in

[#47](https://github.com/GLODI-Engineering/general-mna/issues/47). The loader behind
`kind=filewave` landed in #45 with its tests written in string literals: a few lines each,
chosen to exercise one branch. That is the right shape for a branch and the wrong shape for the
question the module exists to answer, which is whether a capture off an instrument would load.
No real export has reached this project, so the corpus is synthetic and says so — what each
file reproduces is the *shape* a capture arrives in, not any one vendor's bytes, which is also
the level the loader works at, since it skips a preamble by shape precisely so it need not
recognise vendors.

`tests/fixtures/scope-exports/`, nineteen files from a `generate.py` beside them, and
`tests/wave_file_scope_exports.rs`, twenty-seven tests stating each outcome in full — names,
sample count, applied shift, the span of the time base. Not because all of it is interesting,
but because a change in any of it is a change in what a user's capture becomes.

**Writing the corpus found four defects, and the worst one is not the one the file was written
for.** `parse_spice_number` accepts `nan` and `inf`, because Rust's own float parser does and
nothing asked it not to, so a clipped sample becomes a NaN breakpoint and the run goes NaN
later for no visible reason. In the *time* column it is worse: the monotonicity check is
`time < previous`, every comparison with NaN is false, so the check passes and
`partition_point` runs over a list with no total order — documented as unspecified, not as
wrong in some bounded way. [#48](https://github.com/GLODI-Engineering/general-mna/issues/48).

The other three are pinned as they are, each with its test naming the issue that owns it: a
units row displaces the channel names and leaves two outputs called `Volt`, which no `ref=` can
tell apart ([#49](https://github.com/GLODI-Engineering/general-mna/issues/49)); a capture whose
time base is a `Start` and an `Increment` reads its sample index as seconds, so a 10 ms window
spans twenty of them with every sample individually plausible
([#50](https://github.com/GLODI-Engineering/general-mna/issues/50)); a commented header line is
dropped as a comment before the header is looked for, which is how every ASCII logger and
`save -ascii` names its columns ([#51](https://github.com/GLODI-Engineering/general-mna/issues/51)).
And `NoData` — "no line in it begins with a number" — is the message for a file that is almost
entirely numbers, when an older export writes its metadata into the same rows
([#52](https://github.com/GLODI-Engineering/general-mna/issues/52)).

A pinned defect is visible in CI output; an un-pinned one is rediscovered. One expectation of
mine was wrong rather than the code's: `skip=1` on a two-header file leaves the second header to
be read as data, which is what `skip=` counting *the file's* lines means. The test now pins that
semantics through the refusal message instead of asserting the count I expected.

## 2026-11-19 03:18 — one number grammar for every field in the netlist

[general-simulator#57](https://github.com/GLODI-Engineering/general-simulator/issues/57). A dead
time of three hundred nanoseconds could not be written the way the rest of the netlist writes
numbers:

```
PWM1 kind=pwm freq=100000 in=DUTY red=300n fed=300n
-> line 16: device 'PWM1' field 'red' is not a number
```

Device values and `kind=rule` fields went through the SPICE-suffix parser; `kind=` block fields
went through a plain `f64::parse`, which rejects every suffix. Thirteen call sites in
`system_builder.rs` — both `get` closures, four `get_opt` closures, the `pwm` dead-time pair, the
`pspwm` optional reader, `signs`, `const`, `gain` and the `ic` scalars — now go through
`parse_spice_number`. `grep 'parse::<f64>()' src/system_builder.rs` returns nothing.

Nothing that worked before reads differently: `parse_spice_number` tries a plain parse first and
returns it unchanged, so every deck that parsed still parses to the same value. What changes is
only what used to be an error.

**The parser itself got more exact on the way.** Writing the test for it showed `300n` was
3.0000000000000004e-7 while `300e-9` is exactly 3e-7 — because `300.0 * 1e-9` rounds and the
literal does not. The issue had assumed the two spellings were already bit-identical, and for
`200n` they are; for `300n` they were one ULP apart. The suffix is appended as an exponent now
and the string is parsed once, so the two spellings are the same f64 by construction. The
multiplication stays as a fallback for a base the concatenation cannot express — `300.` is a
valid f64 and `300.e-9` is not.

The difference never changed a result. It is the kind of thing that costs an afternoon the day it
finally does, and a test named for it is cheaper than that afternoon.

Three integration tests: a suffixed deck and its exponent twin producing bit-identical `Pwm`
fields, `1m` versus `1meg` in a block field, and `red=soon` still refused by name.
`matches_the_editor_table` still passes — the editor mirrors this grammar and has its own parity
table — but the editor multiplies, so it is now one ULP off for a value like `300n`. That is a
small follow-up in that repository rather than something to leave implied here.

Verification: fmt, clippy, `cargo test --all-targets` — 169 tests.

## 2026-11-19 02:18 — `PULSE` answered with the pulsed value before its own delay

[#39](https://github.com/GLODI-Engineering/general-mna/issues/39). Found while checking whether
gsim-core's catalogue `signal.step` could be mapped onto `kind=pulsewave` (a step is a pulse
whose period outlasts the run). It could not, because the pulse ignored its delay.

`value_at`'s `Pulse` arm clamped the local clock to `0.0` before `td` instead of returning `v1`.
With `tr > 0` that is right by accident -- the rise formula evaluates to `v1` at a local time of
zero. With `tr == 0`, which is the default and how a pulsed source is ordinarily written,
`0.0 < tr` is false, so the clamped clock fell through to the `t < tr + pw` arm and returned the
*pulsed* value from t = 0.

Measured through the built `general-simulator` binary, `PULSE(3 7 0.02 0 0 0.01 0.04)` driving a
`sig2phys` into a `V` source:

| t | before | after | expected |
| --- | --- | --- | --- |
| 0.005 | 7 | 3 | 3 |
| 0.015 | 7 | 3 | 3 |
| 0.02 | 7 | 7 | 7 |
| 0.025 | 7 | 7 | 7 |
| 0.03 | 3 | 3 | 3 |
| 0.065 | — | 7 | 7 |

The fix returns `*v1` early. Two tests were added rather than one: the `tr == 0` case that was
broken, and the `tr > 0` case that was right by accident, so a future rewrite cannot restore the
old behaviour for either. Both sample strictly inside their intervals -- `t = td + pw` exactly is
a floating-point comparison against `tr + pw` and is already pinned by
`pulse_matches_hand_computed_trapezoid`.

Why it survived: that existing test uses `TD=0`, so nothing ever evaluated the function before
the delay. The `Sin` arm's test does make exactly that check ("before td, flat at v0"); the
`Pulse` arm's did not.

**This changes results.** Any deck with a delayed pulsed source and a zero rise time now starts
at `v1` instead of `v2` -- a gate that should be off until `td` is off, a converter that should
start from rest does. Decks whose numbers were accepted against the old behaviour are worth
re-running.

Verification: `cargo test --all-targets` (38 + 70 + 5 + 51), then the deck above through a
rebuilt binary.
