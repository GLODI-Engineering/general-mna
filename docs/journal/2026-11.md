## 2026-11-19 22:09 — a capture holds no NaN

[#48](https://github.com/GLODI-Engineering/general-mna/issues/48), found by the corpus in #47.
`parse_spice_number` falls back to Rust's own float parser, which accepts `nan`, `inf` and
`-inf`, and nothing in the loader asked it not to. A clipped sample therefore became a
breakpoint, and the first step that interpolated across that segment returned NaN for the rest
of the run — with nothing anywhere naming the capture as the cause.

**The time column was the worse half.** The monotonicity check is `if time < previous`, and every
comparison with NaN is false, so a NaN timestamp passed it. The breakpoint list it admitted had
no total order at all, and `segment_before`'s `partition_point` is documented as returning an
*unspecified* index on an unsorted slice — so the waveform was not wrong in some bounded way, it
was arbitrary. That is why the check could not live in the ordering test: by the time the
ordering test could see the problem it had already been defeated by it.

The refusal is a new `WaveFileError::NotFinite` in `number_at`, which is the one place every
time and every value in a capture passes through, so one check covers both columns. Its message
says why `nan` is not a number *here*, which `NotANumber` could not: a capture records a real
signal, and no sample of one is `nan` or `inf`.

Refused in the loader rather than in `parse_spice_number` deliberately, so that only the
loader's contract changed. The same hole is open one level up — `R1 in 0 nan` and `C1 in 0 inf`
both build a netlist today, and solve to NaN everywhere — and that is
[#54](https://github.com/GLODI-Engineering/general-mna/issues/54), because the answer there has a
design question in it (`parse_spice_number` itself, or each field reader?) that this fix did not
need to answer.

Two fixtures went into the corpus with the fix: `nan-timestamp.csv` for the time column and
`infinite-sample.csv` for the other spelling. The corpus test that pinned the old behaviour now
asserts the refusal, which is what a pinned defect is for.

## 2026-11-19 22:03 — nineteen shapes a capture can arrive in

[#47](https://github.com/GLODI-Engineering/general-mna/issues/47). The loader behind
`kind=filewave` landed in #45 with its tests written in string literals: a few lines each,
chosen to exercise one branch. That is the right shape for a branch and the wrong shape for the
question the module exists to answer, which is whether a capture off an instrument would load.
No real export has reached this project, so the corpus is synthetic and says so — what each
file reproduces is the *shape* a capture arrives in, not any one vendor's bytes, which is also
the level the loader works at, since it skips a preamble by shape precisely so it need not
recognise vendors.

`tests/fixtures/scope-exports/`, nineteen files from a `generate.py` beside them, and
`tests/wave_file_scope_exports.rs`, twenty-seven tests stating each outcome in full — names,
sample count, applied shift, the span of the time base. Not because all of it is interesting,
but because a change in any of it is a change in what a user's capture becomes.

**Writing the corpus found four defects, and the worst one is not the one the file was written
for.** `parse_spice_number` accepts `nan` and `inf`, because Rust's own float parser does and
nothing asked it not to, so a clipped sample becomes a NaN breakpoint and the run goes NaN
later for no visible reason. In the *time* column it is worse: the monotonicity check is
`time < previous`, every comparison with NaN is false, so the check passes and
`partition_point` runs over a list with no total order — documented as unspecified, not as
wrong in some bounded way. [#48](https://github.com/GLODI-Engineering/general-mna/issues/48).

The other three are pinned as they are, each with its test naming the issue that owns it: a
units row displaces the channel names and leaves two outputs called `Volt`, which no `ref=` can
tell apart ([#49](https://github.com/GLODI-Engineering/general-mna/issues/49)); a capture whose
time base is a `Start` and an `Increment` reads its sample index as seconds, so a 10 ms window
spans twenty of them with every sample individually plausible
([#50](https://github.com/GLODI-Engineering/general-mna/issues/50)); a commented header line is
dropped as a comment before the header is looked for, which is how every ASCII logger and
`save -ascii` names its columns ([#51](https://github.com/GLODI-Engineering/general-mna/issues/51)).
And `NoData` — "no line in it begins with a number" — is the message for a file that is almost
entirely numbers, when an older export writes its metadata into the same rows
([#52](https://github.com/GLODI-Engineering/general-mna/issues/52)).

A pinned defect is visible in CI output; an un-pinned one is rediscovered. One expectation of
mine was wrong rather than the code's: `skip=1` on a two-header file leaves the second header to
be read as data, which is what `skip=` counting *the file's* lines means. The test now pins that
semantics through the refusal message instead of asserting the count I expected.

## 2026-11-19 03:18 — one number grammar for every field in the netlist

[general-simulator#57](https://github.com/GLODI-Engineering/general-simulator/issues/57). A dead
time of three hundred nanoseconds could not be written the way the rest of the netlist writes
numbers:

```
PWM1 kind=pwm freq=100000 in=DUTY red=300n fed=300n
-> line 16: device 'PWM1' field 'red' is not a number
```

Device values and `kind=rule` fields went through the SPICE-suffix parser; `kind=` block fields
went through a plain `f64::parse`, which rejects every suffix. Thirteen call sites in
`system_builder.rs` — both `get` closures, four `get_opt` closures, the `pwm` dead-time pair, the
`pspwm` optional reader, `signs`, `const`, `gain` and the `ic` scalars — now go through
`parse_spice_number`. `grep 'parse::<f64>()' src/system_builder.rs` returns nothing.

Nothing that worked before reads differently: `parse_spice_number` tries a plain parse first and
returns it unchanged, so every deck that parsed still parses to the same value. What changes is
only what used to be an error.

**The parser itself got more exact on the way.** Writing the test for it showed `300n` was
3.0000000000000004e-7 while `300e-9` is exactly 3e-7 — because `300.0 * 1e-9` rounds and the
literal does not. The issue had assumed the two spellings were already bit-identical, and for
`200n` they are; for `300n` they were one ULP apart. The suffix is appended as an exponent now
and the string is parsed once, so the two spellings are the same f64 by construction. The
multiplication stays as a fallback for a base the concatenation cannot express — `300.` is a
valid f64 and `300.e-9` is not.

The difference never changed a result. It is the kind of thing that costs an afternoon the day it
finally does, and a test named for it is cheaper than that afternoon.

Three integration tests: a suffixed deck and its exponent twin producing bit-identical `Pwm`
fields, `1m` versus `1meg` in a block field, and `red=soon` still refused by name.
`matches_the_editor_table` still passes — the editor mirrors this grammar and has its own parity
table — but the editor multiplies, so it is now one ULP off for a value like `300n`. That is a
small follow-up in that repository rather than something to leave implied here.

Verification: fmt, clippy, `cargo test --all-targets` — 169 tests.

## 2026-11-19 02:18 — `PULSE` answered with the pulsed value before its own delay

[#39](https://github.com/GLODI-Engineering/general-mna/issues/39). Found while checking whether
gsim-core's catalogue `signal.step` could be mapped onto `kind=pulsewave` (a step is a pulse
whose period outlasts the run). It could not, because the pulse ignored its delay.

`value_at`'s `Pulse` arm clamped the local clock to `0.0` before `td` instead of returning `v1`.
With `tr > 0` that is right by accident -- the rise formula evaluates to `v1` at a local time of
zero. With `tr == 0`, which is the default and how a pulsed source is ordinarily written,
`0.0 < tr` is false, so the clamped clock fell through to the `t < tr + pw` arm and returned the
*pulsed* value from t = 0.

Measured through the built `general-simulator` binary, `PULSE(3 7 0.02 0 0 0.01 0.04)` driving a
`sig2phys` into a `V` source:

| t | before | after | expected |
| --- | --- | --- | --- |
| 0.005 | 7 | 3 | 3 |
| 0.015 | 7 | 3 | 3 |
| 0.02 | 7 | 7 | 7 |
| 0.025 | 7 | 7 | 7 |
| 0.03 | 3 | 3 | 3 |
| 0.065 | — | 7 | 7 |

The fix returns `*v1` early. Two tests were added rather than one: the `tr == 0` case that was
broken, and the `tr > 0` case that was right by accident, so a future rewrite cannot restore the
old behaviour for either. Both sample strictly inside their intervals -- `t = td + pw` exactly is
a floating-point comparison against `tr + pw` and is already pinned by
`pulse_matches_hand_computed_trapezoid`.

Why it survived: that existing test uses `TD=0`, so nothing ever evaluated the function before
the delay. The `Sin` arm's test does make exactly that check ("before td, flat at v0"); the
`Pulse` arm's did not.

**This changes results.** Any deck with a delayed pulsed source and a zero rise time now starts
at `v1` instead of `v2` -- a gate that should be off until `td` is off, a converter that should
start from rest does. Decks whose numbers were accepted against the old behaviour are worth
re-running.

Verification: `cargo test --all-targets` (38 + 70 + 5 + 51), then the deck above through a
rebuilt binary.
